# 題材アプリのプロジェクトファイル

#1 の題材「機器の設定＆モニタリング」をプロジェクトスキーマ v0 で記述したもの。P1〜P5 の共通入力。

| ファイル                      | 内容                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------- |
| `device-monitor.source.yaml`  | 手書きの元ファイル（コメントあり、`sampleData` は空）                                   |
| `device-monitor.project.yaml` | 生成物。元ファイルに `src/domain/sample-data.ts` のサンプルデータを入れて正規化したもの |
| `device-monitor.project.json` | 生成物。上と同じ内容の JSON 版                                                          |

**P1〜P5 は `device-monitor.project.yaml`（または同じ内容の `.json`）を読み込む。** 生成物は直接編集せず、元ファイルを直してから再生成する。

```sh
pnpm --filter schema sync:examples   # 元ファイル → 生成物
pnpm --filter schema validate        # 生成物を検証（ファイルを渡すとそのファイルを検証）
pnpm validate                        # ルートからも実行できる
```

生成物が元ファイルと食い違っている場合や、正規化されていない場合はテストが失敗する。

## 収録内容

| ID  | 種別           | id                                        | 内容                                                                                  |
| --- | -------------- | ----------------------------------------- | ------------------------------------------------------------------------------------- |
| S1  | 画面           | `dashboard`                               | 機器ステータス（`repeat` ＋ `StatusBadge`）、メトリクスカード 3 枚、最新アラーム 5 件 |
| S2  | 画面           | `devices`                                 | 機器の `Table`。行クリックで S3 へ                                                    |
| S3  | 画面           | `deviceSettings`                          | `mount` で下書きを `state` に用意し、入力の `change` → `setState`。保存で D1          |
| D1  | ダイアログ     | `saveConfirm`                             | OK で `updateData`（設定と機器の IP）→ 閉じる → S2 へ                                 |
| D2  | ダイアログ     | `alarmDetail`                             | 「確認済みにする」で `updateData`。確認済みならボタンを隠す（`visible`）              |
| —   | コンポーネント | `StatusBadge` / `MetricCard` / `AlarmRow` | props で受け取って表示                                                                |

遷移: S1 → S2、S1 → S3（機器カード）、S1 → D2（アラーム行）、S2 → S1、S2 → S3（行）、S3 → S2（キャンセル）、S3 → D1、D1 → S2。
アクションは 5 種類すべてを使っている。

## JSON と YAML の比較

同じ内容を正規化して書き出したときの量（`sampleData` を除く）:

|                                | JSON                                     | YAML              |
| ------------------------------ | ---------------------------------------- | ----------------- |
| 行数                           | 976                                      | 646               |
| 文字数                         | 28,972                                   | 19,233            |
| `sampleData` の行数            | 1,133                                    | 811               |
| ボタンを 1 つ足したときの diff | +15 行（既存行 `}` → `},` の変更を含む） | +8 行（追加のみ） |

**書きやすさ**

- YAML は引用符・括弧・カンマが無いぶん、手で書くのも読むのも楽。短いものは `{ display: flex, gap: 8 }` のようにフロースタイルで 1 行にでき、画面の構造が追いやすい。コメントも書ける。
- ただし YAML には落とし穴があり、今回すべて踏んだ:
  - `{{` で始まる値はクォートが必須（しないとマッピングになる）。→ ローダーで行番号付きのエラーにした。
  - `border: 1px solid #ddd` は ` #` 以降がコメントになる。クォートが必要。検出できないので気づきにくい。
  - `%`（`unit: "%"`）や `"0"`（`schemaVersion`）などもクォートが必要。
- JSON は冗長だが曖昧さがなく、JSON Schema による補完・検証がエディタでそのまま効く。

**diff の見やすさ**

- YAML の方が diff が小さく、追加したノードがそのまま読める。JSON は前の要素の `}` → `},` の変更が混ざり、ネストが深いと閉じ括弧の行が続く。
- 正規化（キー順の固定）はどちらでも効いており、並び替えによる無駄な diff は出ない。

**正規化して書き出すと失うもの**

- コメントとフロースタイルは書き出し時に消える（元ファイル 530 行 → 生成物 646 行）。エディタがファイルを書き出す運用では、手で書いたコメントは残らない。
- コメントを残したいなら、YAML の Document API で既存ファイルを部分更新する方式が必要になる（v0 では対象外）。

**結論（暫定）**: 人が読む・diff を見る用途には YAML が向いている。ローダーは両方読めるので、形式の最終決定は P2〜P4 でエディタから書き出してみてからでよい。当面の正は YAML 版とする。

## スキーマで表現しにくかった点（P0-3 へのフィードバック）

書けないものは無かったが、次の点は冗長・不自然になった。スキーマ v1 の検討材料にする。

1. **派生値（computed）が無い**。D2 では `data.alarms.find(a => a.id === params.alarmId)` を 5 回書いている。S1 のメトリクスカードは「機器ごとの最新値の最大」を 1 つの長い式で書いた。→ 画面・ダイアログ単位で名前付きの式（`vars: { alarm: "{{ ... }}" }` など）を置けるようにしたい。
2. **表示ラベル・色の対応表が重複する**。`{ online: 'オンライン', ... }` が `StatusBadge` と S2 のテーブルの 2 か所にある。→ 列挙型ごとのラベル・色を定義する場所（定数やデザイントークン）が欲しい。
3. **`Table` のセルにコンポーネントを置けない**。S2 のステータス列は `StatusBadge` を使えず文字列になった。→ `columns[].cell` にノードを書ける形にするか、`repeat` した行で表を組む。
4. **入力のたびに `setState` を書く必要がある**。値のバインディングと `setState.path` が同じパスの二重記述になる（S3 の入力 6 つ）。→ `bind: state.draftSettings.network.ip` のような双方向バインディングの省略記法。
5. **コンポーネントから独自のイベントを出せない**。`AlarmRow` のクリックはインスタンスのルート要素のイベントで代用した。行の中に「確認済みにする」ボタンを置くような場合は書けない。
6. **組み込みノードの props が型付けされていない**。`variant` の値などは自由記述で、typo を検出できない（v0 では意図的に縛っていない。P2〜P4 で決める）。
7. **式の中身は検証されない**。`data.devices` のフィールド名の typo などは実行するまで分からない。`dataModel.source` の型を使ったチェックは P4 で検討。
8. **書き出し時のキー順**。`style` はアルファベット順になるため `display` より `alignItems` が先に来る。レイアウト系（`display` → `flexDirection` → …）を先頭にする順序の方が読みやすい。
9. **日時などの整形手段が無い**。`occurredAt.slice(0, 16).replace('T', ' ')` のように式で書いた。→ フォーマッタ（`formatDate` など）を式から呼べるようにしたい。
