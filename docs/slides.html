P0 schema ─ 思想と特徴

ファイルが正。決定的に書き出し、静的に解析できる

思想

  • 唯一の正: エディタもコード生成もランタイムも、このファイルだけを読み書きする
  • 決定性: 同じ内容なら入力のキー順に関係なく同じテキストになる → git の diff が安定
  • 静的に読める: navigate.to / openDialog.dialog はバインディング不可の固定 id。ファイルから遷移図を作れる
  • 式は JS のまま: {{ 式 }} で埋め込み、独自言語を作らない

特徴

  • node = type / props / style / repeat / visible / events / children
  • 組み込み 7 種: Box・Text・Button・TextInput・NumberInput・Checkbox・Table
  • スコープ: data・state・params・props・event・repeat の変数
  • アクション 5 種: navigate・openDialog・closeDialog・setState・updateData
  • 2 段階の検証: 形（zod の strictObject で typo も検出）→ 参照（id の重複・存在・params の整合）
  • データモデルは TS のソース文字列（dataModel.source）
P0 schema
P0 schema ─ 使い方

プロジェクトファイルを書いて検証する

schemaVersion: "0"
name: 機器モニタリング
entry: devices
screens:
  - id: devices
    name: 機器一覧
    path: /devices
    root:
      id: root
      type: Box
      style: { display: flex, gap: 8 }
      children:
        - id: title
          type: Text
          props: { text: "{{ data.devices.length }} 台" }
          events:
            click:
              - { type: navigate, to: dashboard }
sampleData:
  devices: [...]
  1. YAML（または JSON）でファイルを書く。先頭に $schema を書くとエディタで補完が効く
  2. 検証する 
    pnpm validate                 # 題材を検証
pnpm --filter @ui-editor/schema validate <file>
  3. コードから使う: const r = loadProject(text, "yaml")（読込と検証をまとめて行う）→ r.success なら serializeProject(r.project, "yaml")
  4. スキーマを変えたら JSON Schema を再生成 
    pnpm --filter @ui-editor/schema gen:json-schema

注意 YAML では {{ で始まる値は必ずクォート（ローダーが行番号付きで検出）。#ddd や % もクォートが必要。

P1 codegen ─ 思想と特徴

「手で書いた React」と同じ形のコードを、純粋関数で

思想

  • 読める生成コード: 1 画面 = 1 ファイル、CSS のクラス名 = エディタ上のノード id。生成後は人が育てる前提
  • 決定性: generate(project) → {path, content}[] は純粋関数。依存バージョンも Prettier 設定もコード内に固定し、日時・絶対パスは出さない
  • 式は書き換えない: {device.name} のように、書いた式がそのまま出る。acorn でスコープ外の名前を生成時にエラーにする

特徴

ファイル 変換
Box <div> ＋ styles.nodeId
repeat / visible {each.map(...)} / {式 && <…>}
navigate react-router ＋ paths.xxx(params)
openDialog ストアの dialog ＋ DialogHost
setState / updateData Zustand ストアのアクション
events.mount useEffect

比較用に Redux Toolkit 版のストアも出力できる（generateRtkStore）。読みやすさで Zustand を採用。

P1 codegen
P1 codegen ─ 使い方

プロジェクトファイル → 動くアプリ

  1. 生成器をビルド 
    pnpm --filter @ui-editor/codegen build
  2. 生成する（検証エラーがあれば箇所を表示して止まる） 
    pnpm --filter @ui-editor/codegen gen \
  packages/schema/examples/device-monitor.project.yaml \
  --out ../my-app --clean
  3. 生成したアプリを起動 
    cd ../my-app && pnpm install && pnpm dev   # :5178

オプション

  • --name: 生成アプリの package 名（省略時はファイル名から）
  • --clean: 出力先の src/ を消してから書く（node_modules には触らない）

生成器を直したら

pnpm --filter @ui-editor/codegen snapshots:update
pnpm --filter @ui-editor/codegen build:examples

生成結果は snapshots/ にそのまま置いてあり、生成器の変更は生成コードの diff としてレビューできる。

P2 editor-puck ─ 思想と特徴

標準的な操作感を最小のコードで手に入れる

思想

  • 完成品に乗る: パレット・アウトライン・右パネル・パンくず・undo/redo・ビューポート切替・ズームは Puck 付属
  • 名前を読み替えない: Puck のコンポーネント名 = P0 の type
  • Puck の形式はファイルに出さない: 開いているツリーだけを Puck データにし、変更のたびに P0 に戻す（convert.ts 約 140 行）

特徴

  • Puck で編集できない repeat / visible / events は props._p0 に退避して保つ
  • 題材の全画面を往復させても1 文字も変わらない（テストで確認）
  • プロジェクトの components がパレットに自動で並ぶ。インスタンスの欄も props 定義から生成
  • 「選択をコンポーネント化」で既存のパーツを部品に切り出せる
  • style 欄は Puck の object フィールド＋カスタム欄。候補は StyleSchema（zod）から

弱点: 右パネルのレイアウトの自由度が低い／入れ子の入れ物へのドロップが狙いにくい／JS 約 1.44 MB

P2 editor-puck
P2 editor-puck ─ 使い方

画面を組み立てて P0 形式で保存する

  1. 起動。前回の作業（localStorage）か、題材ファイルが開く 
    pnpm --filter @ui-editor/editor-puck dev
  2. 上部のタブで画面・ダイアログ・コンポーネントを切り替える。「＋ 新規」で新しく作る
  3. 左のパレットからキャンバスへパーツをドラッグ（Container / Text / Button / Input / Table …）
  4. 右パネルで props を入力。値は固定値でも {{ 式 }} でもよい
  5. 右パネルの「スタイル」で幅・高さ・padding・flex・border などを設定
  6. repeat / events などは「詳細（JSON）」欄で入力
  7. ツールバーの「保存」で YAML / JSON をダウンロード（保存前に検証）

コツ

  • padding / gap が 0 の入れ物は境目が無く狙いにくい。作る間は padding を付け、最後に消す
  • コンポーネントのタブでは上部で props（名前・TS の型・既定値）を定義し、中から {{ props.名前 }} で参照
  • キャンバスは画面の式を評価せず式のまま表示（コンポーネント内の props だけ評価） 
# UI 操作で S1〜S3 を作り直す評価スクリプト
pnpm --filter @ui-editor/editor-puck eval:rebuild

apps/editor-craft@craftjs/core:5175
P3 editor-craft ─ 思想と特徴

欲しい UI を制約なく作れる「組み立て型」

思想

  • 骨組みだけ借りる: Craft.js が担うのは選択・ドラッグ＆ドロップ・ノードツリー・undo
  • P0 が正: 開いているドキュメントの root だけを Craft に読み込み、変化のたびに P0 に書き戻す
  • 見た目を共通化: parts/view.tsx をキャンバスとコンポーネントのプレビューで共用

特徴

  • P0 のフィールドを Craft の props にそのまま入れるので退避が不要。ルートが 1 つの P0 とそのまま合う
  • 自由な style パネル: グループ・2 列・横並び/縦並びボタン・キャンバス上のリサイズハンドル
  • キャンバスでバインディングをサンプルデータで評価して表示（repeat は 1 件目）
  • events の GUI（params の無い画面遷移・ダイアログ開閉）
  • S1〜S3 を UI 操作で作り直すとノードのツリーは題材と完全一致（画面の events.mount は作れない）

弱点: UI をすべて書くので P2 の約 2 倍のコード／Craft.js は 2025-02 以降リリースが無い／HTML5 DnD でタッチ非対応

P3 editor-craft
P3 editor-craft ─ 使い方

パレット → レイヤー → プロパティの順に作る

  1. 起動すると題材（device-monitor.project.json）が開く 
    pnpm --filter @ui-editor/schema build   # 初回のみ
pnpm --filter @ui-editor/editor-craft dev
  2. 左の「新規作成」で画面・コンポーネント・ダイアログを作る（空の Box が root）
  3. パレットのクリック／ドラッグでパーツを置き、レイヤーで選択・並べ替え
  4. 右のプロパティ欄と style 欄で編集。キャンバス上のハンドルでリサイズ
  5. 「events」で click に画面遷移・ダイアログを割り当てる（それ以外は「詳細（JSON）」）
  6. 「JSON で保存」「YAML で保存」（検証結果を一覧表示）

部品化の流れ

  1. パーツを選んで「コンポーネント化」
  2. 元の場所がインスタンスに置き換わる
  3. 右の「ドキュメント」で props を定義
  4. 「〜を開く」で中身を編集 → インスタンスにすぐ反映

まだできないこと

  • 画面の events.mount の編集（読込値は保たれる）
  • プレビュー用の params / state の値

P2 と P3 の比較

「完成品に乗る」か「組み立てる」か

観点 P2: Puck（完成品） P3: Craft.js（組み立て型）
エディタの UI ほぼ付属。自前はタブ・ツールバー・props 定義欄 すべて自前
実装量（src） 約 1,840 行 ＋ CSS 285 行 約 2,300 行 ＋ CSS 620 行
依存・サイズ 推移的に 36 個 / JS 1.44 MB（gzip 430 kB） 推移的に 7 個 / JS 601 kB（gzip 172 kB）
S1〜S3 の作り直し S3 の入れ子 1 つを作れず。操作数 61 / 35 / 78 ツリーは完全一致（画面の mount イベントを除く）。操作数 99 / 28 / 130
P0 との相性 root の扱いに回避策が 2 つ要った そのまま合う
ライブラリの状態 活発（0.x で API が変わる） 停滞（fork して持つ覚悟が要る）

判断の目安: 標準的なページビルダーの操作感で十分なら Puck。スタイルパネル・リサイズ・イベント GUI など
エディタの見た目と操作を自分たちで決めたいなら、組み立て型（または自作寄り）。

P4 runtime ─ 思想と特徴

純粋関数のエンジン ＋ 5 つのタブの UI

思想

  • UI から切り離す: packages/runtime は純粋関数だけ。エディタのプレビューにも、生成コードの振る舞いの基準にも使える
  • アクション = 状態 → 状態: runActions(project, state, actions) は新しい状態とログを返す。reducer に載り、ログ・やり直し・テストが簡単
  • TS 型をスキーマとして使う: dataModel.source を構文木だけで解析（型チェッカー不要）
  • JS の式を安全寄りに: TS パーサーで検査 → new Function。例外は投げず { ok: false, error }

式の検査で弾くもの

  • スコープ外の名前（window / fetch など）
  • 代入・++・delete・this
  • constructor / __proto__ への参照
  • 状態は深く凍結 → sort() などの破壊的操作もエラー

主な export

parseDataModel checkSampleData evaluateExpression evaluateTemplate collectBindings suggest runActions

P4 runtime-preview ─ 使い方

5 つのタブで、データ・式・イベントを確かめる

タブ できること
プレビュー 題材アプリを実際に操作。右に表示中の画面・ダイアログ・state・イベントごとの実行ログ。式のエラーは ⚠
データモデル TS の型一覧と詳細。フォームでフィールドを追加・編集すると TS ソースを書き出す
サンプルデータ コレクションごとの表。型に合わせた入力で編集・追加・複製・削除。型違反は赤
式 補完つきで式を試す。プロジェクト内の全式と、その場所で使える名前の一覧
イベント ノードを選び click / change / rowClick / mount にアクションを割り当て、並べ替え、試し実行
  1. 起動 
    pnpm --filter @ui-editor/runtime-preview dev
  2. 「プレビュー」で S1 → S2 → S3 → 保存 → D1 と操作し、ログと state を確認
  3. 「式」で data.devices.find(d => d. と打って補完を試す
  4. 「サンプルデータ」「イベント」で編集し、プレビューに戻って確認
  5. ヘッダーの「保存」で検証して P0 形式で書き出す

タブは URL の hash（#sampleData など）に残る。

P5 flow ─ 思想と特徴

「どのボタンでどこへ行くか」を一目で

思想

  • ファイルから静的に作る: 遷移先が固定 id なので、実行せずに遷移図が描ける（P0 の設計の成果）
  • 遷移だけを担当: ツリー・props・style は読むだけ。同じ events の中の他のアクションは残したまま、遷移だけ足し引きする
  • 住所で書き換える: 遷移の id は起点の住所
    screen:dashboard/alarmRow#click[0]

特徴

  • 線は起点のパーツ（ボタン・カード・行）から出る。navigate は実線、openDialog は破線
  • ノードはワイヤーフレーム表示。repeat は ×n、条件表示は if バッジ
  • dagre の自動配置 ＋ 手動配置（layouts/*.layout.json に別保存）
  • プロトタイプモード: ホットスポットをクリックして遷移を再生。mount のリダイレクトも追う
  • 検証結果をツールバーに常時表示
P5 flow
P5 flow ─ 使い方

線を引いて遷移を作り、プロトタイプで確かめる

  1. 起動すると題材の遷移図が描かれる（「ファイルを開く」で他の P0 ファイルも） 
    pnpm --filter @ui-editor/flow dev
  2. 追加: ノードにマウスを乗せ、パーツ右端の点から画面・ダイアログへドラッグ。画面なら navigate、ダイアログなら openDialog
  3. 編集: 線を選ぶとパネルにイベント・params。必須 params の空欄は赤枠
  4. 削除: 線を選んで Delete／パネルの「この遷移を削除」
  5. ノードを動かしたら「配置を保存」、内容は「プロジェクトを保存」

プロトタイプモード

  1. 「▶ プロトタイプ」またはノードをダブルクリック
  2. 光るホットスポットをクリックして進む（それ以外をクリックすると場所が光る）
  3. 「戻る」「最初から」、右側に実行ログ
  4. 「遷移図に戻る」で最後の画面を選択

setState / updateData と式は評価しない（ログに残すだけ）。見た目の確認は P4 で。

保存: Chrome / Edge では File System Access API で開いたファイルに上書き。

P6 tauri ─ 思想と特徴

差し替え口だけで Web のコードを共有する

思想

  • エディタは書き換えない: @ui-editor/editor-craft を workspace 依存にして直接 import
  • 差し替え口: P3 の App の onDownload をローカル書き込みにつなぐだけ
  • 最小権限: capabilities は dialog の open/save と fs の読み書きだけ。ダイアログで選んだパスだけが許可される
  • git 運用と相性が良い: 「開いて直して上書き」がそのままできる

P6 tauri ─ 使い方

開発起動からアプリのビルドまで

  1. Rust ツールチェーンと OS の前提（macOS: Xcode、Windows: MSVC + WebView2、Linux: WebKitGTK）を用意
  2. 開発起動（Vite を :5179 で起動し、そのウィンドウを開く。HMR あり） 
    pnpm install
pnpm --filter @ui-editor/schema build
pnpm --filter @ui-editor/tauri tauri dev
  3. 上のバーの「ローカルのファイルを開く…」で .json / .yaml を開く
  4. 編集して「JSON で保存」「YAML で保存」→ 同じ形式ならダイアログなしで上書き、形式を変えると保存先を聞く
  5. 配布用にビルド 
    pnpm --filter @ui-editor/tauri tauri build   # .app / .dmg

知っておくこと

  • 初回は Rust のクレート約 350 本をコンパイル（数十秒〜数分）
  • pnpm -r build はフロントエンドだけ（Rust はビルドしない）
  • ブラウザだけで見るなら pnpm --filter @ui-editor/tauri dev（Tauri API は使えない）
  • npm と Rust のマイナーバージョンを揃える（2.11 系に固定）
  • 署名なしビルドは他の Mac で Gatekeeper に止められる
P6 tauri
横断して見えたこと

複数のツールで同じ不足に行き当たった

  • 派生値（computed / vars）が無い
    D2 で同じ find を 5 回書く。生成コードにも重複が出る（P0・P1・P4）
  • コレクションと型の対応が無い
    devices → Device を名前の規約で推測（P1・P4）
  • コンポーネントの独自イベントが無い
    AlarmRow のクリックはルート要素で代用（P0・P4・P5）
  • 書き出しでキー順が変わる
    props 定義の宣言順が失われる（P1・P2）
  • エディタ用情報の置き場所
    遷移図の座標 → トップレベルに editor 名前空間を提案（P5）
  • アクションの不足
    レコード追加・削除、条件分岐、通知、戻る、非同期（P4）
  • プレビュー用の値
    params や mount 後の state がエディタに無い（P2・P3）
  • 式の型チェック
    device.nmae の typo は実行しても見つからない（P1・P4）

どのツールを、いつ使うか

やりたいこと ツール ポイント
画面を定義する・検証する P0 schema YAML で書いて pnpm validate。すべての出発点
本番コードの叩き台を得る P1 codegen 決定的・読める React。生成後は人が育てる
手早く画面を並べる P2 Puck 少ないコードで標準的なエディタ体験
エディタ UI を作り込む P3 Craft.js 自由な UI。コード量と保守は自分持ち
動きとデータを確かめる P4 runtime 生成せずに実行。式・型・アクションの検査
画面のつながりを設計する P5 flow 線で遷移を編集し、プロトタイプで再生
ローカルで上書き保存したい P6 tauri P3 をそのまま包む。配布コストは増える

共通の約束はひとつ ─ プロジェクトファイルが唯一の正。だからツールを組み合わせても、差し替えても、保存形式は変わらない。
