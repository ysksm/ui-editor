画面遷移と ER 図から動くアプリを組み立てる
オリジナル UI エディタ 要求仕様（案）

2026-10-23 ・ 対象: original-poc/ ・ 版: draft 0.1

1概要と目的

Plasmic のように「ビジュアルに定義したものが、そのまま動くアプリになる」ツールを、既存ライブラリのエディタに乗らないオリジナル実装として段階的に作る。最初の関心は見た目の作り込みではなく、画面の構成・画面同士の関係・データの関係を定義して実際に動かすことにある。

画面とダイアログの関係

画面一覧、画面間の遷移、ダイアログの呼び出し元を定義して、図で見られるようにする。

何で遷移するか

ボタン、表の行クリック、選択してからボタン、といったトリガーを遷移ごとに定義する。

データ操作

追加・更新・削除（CRUD）のアクションでサンプルデータを書き換えながら、プレビューで動かす。

ER 図とサンプルデータ

エンティティとリレーションを定義し、そこから整合したサンプルデータと画面のひな形を作る。

作り始める入口は 2 つ用意する。フロー先行 画面と遷移から考えるパターンと、ER 先行 データ構造から考えて画面を生成するパターン。どちらから始めても、最後は同じ 1 つのプロジェクト JSON にまとまる。

3既存資産との関係

このリポジトリには P0〜P6 の検証成果がある。オリジナル PoC はそれらを置き換えるものではなく、得た知見を土台に、自前で一貫した道具を作る位置づけにする。

既存 そのまま生かすもの オリジナル PoC で新しく足すもの
packages/schema（スキーマ v0） screens / dialogs / params、{{ }} バインディング、アクション（navigate / openDialog / closeDialog / setState / updateData）、2 段階の検証、決定的な書き出し ER（entities / relations）、宣言的な遷移（transitions）、選択状態、createRecord / deleteRecord、画面の役割（一覧・詳細など）
apps/flow（P5 遷移図） React Flow による画面・ダイアログのノード表示、遷移の追加・削除の操作感 画面の中身がまだ無い状態でも遷移を引けること（判断 D1）
apps/runtime-preview（P4） プロジェクトファイルを解釈して動かす方式 CRUD とリレーションを考慮したデータストア
Puck / Craft.js（P2・P3） 画面内のレイアウト編集の知見 後半のステップで、必要な範囲だけ自前で作る
題材「機器の設定＆モニタリング」 Device / DeviceSettings / Metric / Alarm と既存の画面構成を、検証用の題材としてそのまま使う ER として書き直したもの
方針 スキーマは v0 を拡張した poc-0 として original-poc/ 内に新しく持つ。v0 と互換を保つことは必須にしないが、v0 形式への書き出しはできるようにして、既存の codegen / runtime-preview / flow でも開けるようにする（Should）。

4全体コンセプト

すべての編集画面は、1 つのプロジェクト JSON を別の角度から見て編集するビューにする。フロー図・ER 図・画面エディタ・プレビューは同じデータを共有し、どこで編集しても他のビューに反映される。

入口 A：フロー先行

  • 画面・ダイアログを名前だけで作り、図に並べる
  • 画面同士を線でつなぎ、トリガー（ボタン／行クリックなど）を選ぶ
  • この時点で、ワイヤーフレームのプレビューで遷移を辿れる
  • 後から画面に「どのエンティティを扱うか」を結びつける

入口 B：ER 先行

  • エンティティ・属性・リレーションを ER 図で定義する
  • リレーションを守ったサンプルデータを生成する
  • エンティティごとに「一覧・詳細・編集ダイアログ・削除確認」と、その間の遷移を生成する
  • 生成されたものは入口 A のフロー図にそのまま現れ、手で直せる

5主要な設計判断（推奨案）

実装を始める前に決めておきたい 3 点。それぞれ推奨案を置き、13 章で確認する。

D1. 遷移の正をどこに置くか

v0 では、遷移は画面内の部品のイベントに書いたアクション（navigate.to）から導いている。フロー先行では画面の中身がまだ無いので、この方式だと遷移を引けない。

案 内容 利点 欠点
(a) 推奨
宣言的な遷移		 トップレベルの transitions に「from・to・トリガー・渡す値」を持つ。トリガーが参照する部品は後から結びつける（未結合を許す） 中身が無い画面でも遷移を定義できる。遷移図をファイルから静的に作れる。未結合・不整合を検証で指摘できる 部品側のイベントと遷移の 2 か所に情報が分かれるので、対応を保つ仕組みが要る
(b) 仮の部品を生成 遷移を引くと、遷移元の画面に仮のボタンを自動で置き、そのイベントに navigate を書く v0 の構造のまま 画面設計前から部品が増えて散らかる。トリガーの種類を後から変えにくい

(a) を採る場合、部品のイベントには「遷移 id を実行する」アクション（{ type: "transition", id: "..." }）だけを書き、遷移の中身は transitions に一元化する。プレビューは、部品が未結合の遷移を画面下部の「未結合の遷移」ボタンとして出し、フロー先行の段階でも辿れるようにする。

D2. サンプルデータを入れ子で持つか、フラットに持つか

案 保存形式 利点 欠点
(a) 推奨
フラットを正、入れ子は派生		 エンティティごとの配列（data.Device[], data.Alarm[]）を外部キーでつなぐ ER 図とそのまま対応する。多対多や複数の親を持つデータも表せる。CRUD が単純 入れ子で見たいときは変換が要る（ビューと書き出しで対応）
(b) 入れ子を正 Device[].alarms[] のように親の中に子を持つ 人が読みやすい。親を消すと子も消える（カスケード削除）が自然に表せる 多対多・複数の親で破綻する。同じデータが複数箇所に出ると更新がずれる

(a) を採っても、リレーションに onDelete: "cascade" を持たせればカスケード削除は表現できる。ER 図ビューとデータ編集画面には「親から子をたどる入れ子表示」を用意し、JSON 書き出しにも入れ子形式を選べるようにする。

D3. 画面の中身の表現

画面の中身は v0 と同じノードの木（type / props / children / events）で持つ。ただし初期のステップでは自由なレイアウト編集はせず、画面に役割（kind）を持たせ、役割ごとのテンプレートから中身を作る（一覧 = 表＋操作ボタン、詳細 = 項目の並び、フォーム = 入力欄＋保存）。自由編集はステップ 6 以降に回す。

6データモデル案（poc-0）

題材「機器の設定＆モニタリング」で書いた例。キー名は仮のもの。

{
  "schemaVersion": "poc-0",
  "name": "機器の設定＆モニタリング",
  "entry": "devices",

  "entities": [
    {
      "id": "Device", "name": "機器", "primaryKey": "id", "displayField": "name",
      "fields": [
        { "id": "id",       "type": "id" },
        { "id": "name",     "type": "string", "required": true },
        { "id": "model",    "type": "string" },
        { "id": "status",   "type": "enum", "values": ["online", "offline", "warning"] },
        { "id": "ipAddress","type": "string", "format": "ipv4" }
      ]
    },
    {
      "id": "Alarm", "name": "アラーム", "primaryKey": "id", "displayField": "message",
      "fields": [
        { "id": "id",           "type": "id" },
        { "id": "deviceId",     "type": "ref", "entity": "Device" },
        { "id": "level",        "type": "enum", "values": ["info", "warn", "error"] },
        { "id": "message",      "type": "string" },
        { "id": "acknowledged", "type": "boolean", "default": false }
      ]
    }
  ],

  "relations": [
    { "id": "deviceAlarms", "from": "Alarm.deviceId", "to": "Device.id",
      "cardinality": "many-to-one", "onDelete": "cascade" }
  ],

  "data": {
    "Device": [ { "id": "dev-001", "name": "ルータ A", "status": "online", "...": "..." } ],
    "Alarm":  [ { "id": "alm-001", "deviceId": "dev-001", "level": "warn", "...": "..." } ]
  },

  "state": {
    "selection": { "Device": null }
  },

  "screens": [
    { "id": "devices", "name": "機器一覧", "kind": "list", "entity": "Device", "path": "/devices",
      "root": { "id": "page", "type": "Box", "children": ["..."] } },
    { "id": "deviceDetail", "name": "機器詳細", "kind": "detail", "entity": "Device",
      "path": "/devices/:deviceId", "params": { "deviceId": { "type": "string" } } }
  ],

  "dialogs": [
    { "id": "deviceEdit",    "name": "機器の編集", "kind": "form",    "entity": "Device" },
    { "id": "deviceDelete",  "name": "削除の確認", "kind": "confirm", "entity": "Device" }
  ],

  "transitions": [
    { "id": "t1", "from": "devices", "to": "deviceDetail",
      "trigger": { "type": "rowClick", "node": "deviceTable" },
      "params": { "deviceId": "{{ event.row.id }}" } },
    { "id": "t2", "from": "devices", "to": "deviceEdit",
      "trigger": { "type": "click", "node": "editButton", "requires": "selection.Device" },
      "params": { "deviceId": "{{ state.selection.Device.id }}" } }
  ]
}

モデルの要点

  • entities / relations：ER 図の正。フィールドの型は id / string / number / boolean / date / enum / ref から始め、ref がリレーションの外部キーになる。
  • data：エンティティ id → レコードの配列（D2 の案 a）。{{ data.Device }} で参照する。
  • state.selection：エンティティごとの「いま選ばれているレコード」。表で行を選ぶと入り、「選択してからボタン」の遷移で使う。
  • screens / dialogs：v0 と同じ形に kind（役割）と entity（扱うエンティティ）を足す。root は省略可（中身の無い画面を許す）。
  • transitions：D1 の案 a。trigger.node は省略可（未結合）。
  • 保存は JSON（木構造）。キー順を固定した決定的な書き出しで、差分が読みやすいようにする（v0 と同じ方針）。

7遷移とアクション

遷移のトリガー（何によって遷移するか）

パターン トリガー 遷移先に渡す値 例
T1 単純遷移 ボタンなどの click 固定値、または無し ダッシュボード →「機器一覧へ」→ 機器一覧
T2 行クリック遷移 表の rowClick クリックした行（event.row）の値 機器一覧の行 → その機器の詳細
T3 選択＋ボタン遷移 表で行を選ぶ（rowSelect → state.selection）→ ボタンの click 選択中のレコード（state.selection.X）。未選択ならボタンを無効にする（requires） 機器を選んで「編集」→ 編集ダイアログ
T4 ダイアログ呼び出し T1〜T3 のどれかで、遷移先がダイアログ 同上 機器詳細の「削除」→ 削除確認ダイアログ
T5 画面表示時 画面の mount — 条件を満たさなければ別画面へ（Could）

遷移には付随アクションを持たせられる。たとえば「削除確認で OK → deleteRecord → ダイアログを閉じる → 一覧へ戻る」は、遷移 1 本の前後に並んだアクション列として表す。

アクション一覧

種類 アクション 内容 v0 との関係

openDialogダイアログを開くv0 と同じ
closeDialogダイアログを閉じる。結果（OK / キャンセル）を返し、呼び出し元で分岐できる結果の受け渡しを追加

9非機能要求

ID要求
NFR-01ブラウザだけで動く（サーバー不要）。Chrome / Edge の最新版を対象にする。ファイルの上書き保存は File System Access API、無ければダウンロード
NFR-02プロジェクト JSON は人が読んで git で差分を見られること。配置情報など見た目だけの情報は分けて保存する
NFR-03スキーマにバージョンを持たせ、変わったときは移行関数で古いファイルを読めるようにする
NFR-04画面 50・エンティティ 30・レコード 合計 5,000 件程度でも、編集とプレビューが体感で遅くならない
NFR-05スキーマ・検証・データストア（CRUD とカスケード）・サンプル生成はユーザーインターフェースから切り離したライブラリにし、単体テストを書く
NFR-06{{ }} の式は PoC では JS として評価する（信頼できるファイルだけを開く前提）。外部に公開する段階で安全な式評価に置き換える

10ステップ計画

各ステップは単体で動かして確認できる大きさにする。フロー先行 の流れ（ステップ 1・2）と ER 先行 の流れ（ステップ 3）は独立しているので、順番は入れ替えられる。ステップ 4・5 で 2 つが合流する。

STEP 0スキーマ poc-0 と検証・保存
  • zod で 6 章のスキーマを書き、形と参照の検証、決定的な書き出し、JSON の読み書きを作る
  • 題材「機器の設定＆モニタリング」を poc-0 で書いたサンプルを用意する

完了条件：サンプルを読み込み → 書き出し → 再読み込みで内容が変わらない。存在しない画面への遷移などを、場所付きのエラーとして出せる。

STEP 1画面一覧とフロー図フロー先行
  • 画面・ダイアログの一覧（作成・名前変更・削除）と、それをノードにしたフロー図
  • ノードをつないで遷移を作る（ダイアログ宛ては破線）。自動レイアウト、Undo / Redo、保存

完了条件：題材の 3 画面・2 ダイアログと遷移を、ゼロから 5 分程度で作って保存し、開き直せる。

STEP 2トリガー定義とワイヤーフレームのプレビューフロー先行
  • 遷移のパネルでトリガー（T1〜T4）、渡す値、付随アクションを設定する
  • ダイアログの呼び出し元一覧、画面ごとの入出力の遷移一覧、警告（到達不能・未結合）
  • 中身の無い画面を「タイトル＋出ていく遷移のボタン」として表示するプレビューで、クリックして辿る。フロー図上で現在地を強調

完了条件：ダッシュボード → 機器一覧 → 機器詳細 → 削除確認ダイアログ → 一覧に戻る、をプレビューで辿れる。

STEP 3ER 図とサンプルデータER 先行
  • エンティティ・属性・リレーションの編集と ER 図表示
  • 件数とシードを指定したサンプルデータ生成。表形式での編集、入れ子表示

完了条件：Device / Alarm / Metric / DeviceSettings の ER を作り、機器 5 件・アラーム 20 件を、外部キーが壊れていない状態で生成できる。

STEP 4データのバインドと CRUD の実行合流合流
  • 画面に役割（一覧・詳細・フォーム・確認）とエンティティを設定し、役割ごとのテンプレートで表示する
  • 選択状態（state.selection）、行クリック・選択＋ボタンの遷移、CRUD アクション、カスケード削除をプレビューで実行する
  • データのリセット、アクションのログ、v0 形式への書き出し

完了条件：機器を選んで編集・保存すると一覧に反映される。機器を削除すると、その機器のアラームも消える（cascade）。

STEP 5ER からの画面・遷移の生成ER 先行
  • エンティティから一覧・詳細・フォーム・削除確認と、その間の遷移を生成する。親の詳細に子の一覧を入れる
  • フロー先行で作った画面に、後からエンティティを設定して中身を生成する
  • ER の変更が画面・遷移・データに与える影響の表示

完了条件：空のプロジェクトから ER だけを作り、ボタン 1 つで「機器の一覧・詳細・編集・削除」が動くアプリになる。

STEP 6画面の中身の編集とコード書き出し
  • 部品の追加・並べ替え・props のバインディング、部品と未結合の遷移の結びつけ
  • React のソースコード書き出し（packages/codegen を拡張、または v0 経由）

完了条件：生成された機器詳細画面にボタンを足して新しい遷移に結びつけ、書き出したコードがプレビューと同じように動く。

12スコープ外（PoC ではやらないこと）

  • 実際のバックエンド・データベースとの接続（データはプロジェクト JSON 内のサンプルデータのみ）
  • 認証・権限・複数人での同時編集
  • ピクセル単位のデザイン編集（Figma のような自由配置）、テーマ・デザインシステム
  • レスポンシブ対応・アクセシビリティの作り込み（プレビュー画面側）
  • 任意の JS を書けるスクリプト機能（式は {{ }} の範囲のみ）

13確認したいこと

次に進む前に 下の項目は推奨案のまま進めても作業は始められる。違う場合だけ指摘してもらえれば、この文書を直してからステップ 0 に入る。
  • 「クラウド操作」は CRUD 操作の意味でよいか
  • 「カスケード構造」は、プロジェクト定義の木構造（A）の意味か、サンプルデータを親子で入れ子に持つ（B）意味か。B の場合、D2 の「フラットを正、入れ子は派生」でよいか
  • D1：遷移を宣言的な transitions として持ち、部品とは後から結びつける方式でよいか
  • 題材は既存の「機器の設定＆モニタリング」でよいか。別の題材（例: 受注管理など、多対多を含むもの）も用意したいか
  • 最初に作るのはフロー先行（ステップ 1・2）からでよいか。ER 先行（ステップ 3）を先にしたいか
  • 最終的に欲しいのは「動くプロトタイプ」までか、「書き出したコードを本番の土台にする」ところまでか（ステップ 6 の比重が変わる）
  • GitHub の issue に分けて進めるか（既存の P0〜P6 と同じ運用にするか）
