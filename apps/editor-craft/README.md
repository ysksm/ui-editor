# editor-craft（P3: Craft.js の画面エディタ）

#19 のプロトタイプ。Craft.js（エディタを組み立てるためのフレームワーク）で、パレット・キャンバス・レイヤー・プロパティパネルを自前で組んだ画面エディタ。

```sh
pnpm --filter @ui-editor/schema build   # 初回のみ（スキーマの dist を使う）
pnpm --filter @ui-editor/editor-craft dev   # http://localhost:5175
```

起動すると題材ファイル（`packages/schema/examples/device-monitor.project.json`）を開く。

## 構成

| ファイル                   | 内容                                                                   |
| -------------------------- | ---------------------------------------------------------------------- |
| `src/project/convert.ts`   | P0 のノード ⇔ Craft.js のシリアライズ形式の変換                        |
| `src/project/documents.ts` | 画面・コンポーネント・ダイアログ（エディタで開く単位）の一覧と差し替え |
| `src/project/evaluate.ts`  | キャンバス表示用の `{{ }}` の評価（評価できなければ文字列のまま）      |
| `src/parts/view.tsx`       | パーツの見た目（キャンバスとコンポーネントのプレビューで共通）         |
| `src/parts/craft.tsx`      | Craft.js の resolver に登録するコンポーネント                          |
| `src/editor/*`             | パレット・レイヤー・プロパティパネル                                   |

- 状態は P0 のプロジェクト（`Project`）を正として持ち、開いているドキュメントだけを Craft.js に読み込む。Craft の状態が変わるたびに P0 形式に戻してプロジェクトに書き戻す。
- コンポーネントのインスタンスは 1 種類の Craft コンポーネント（`ComponentInstance`）で表す（Craft の resolver は起動時に固定されるため）。

## 保存・読込（P0 形式）

ツールバーの「開く」で `.json` / `.yaml` を読み込み（`loadProject` で検証）、「JSON で保存」「YAML で保存」で `serializeProject` の出力をダウンロードする。保存時に `validateProject` で検証し、問題があれば一覧を表示する（書き出しはする）。

### Craft.js の形式との対応

| P0                                                  | Craft.js（`SerializedNodes`）                                                                 |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| ノード 1 つ                                         | ノード 1 つ。Craft の id はルートが `ROOT`、それ以外は P0 の id（重複時は `~2` などを付ける） |
| `type`（組み込み）                                  | `type.resolvedName`（Box / Text / …）                                                         |
| `type`（コンポーネント）                            | `resolvedName: "ComponentInstance"` ＋ `props.component`                                      |
| `id`                                                | `props.nodeId`                                                                                |
| `props` / `style` / `repeat` / `visible` / `events` | `props` の同名キーにそのまま                                                                  |
| `children`（Box）                                   | `isCanvas: true` と `nodes`                                                                   |
| `children`（Box 以外）                              | `custom.p0Children` に退避してそのまま戻す                                                    |

画面の `name` / `path` / `params` / `events`、コンポーネントの `props` 定義、`dataModel` / `state` / `sampleData` は Craft に渡さず、P0 のプロジェクトにそのまま残す。Craft に読み込むのは開いているドキュメントの `root` だけ。

### 変換で失われる情報

- 題材ファイル（全画面・コンポーネント・ダイアログ）は、読込 → Craft.js に読み込み → 保存でファイルとバイト単位で一致する（`src/project/roundtrip.test.tsx`。JSON → JSON、JSON → YAML、YAML → JSON）。
- 失われるのは Craft.js 側だけの情報: `hidden`、`linkedNodes`、選択状態、undo 履歴（ドキュメントを切り替えると消える）。いずれも P0 に対応するものが無い。
- エディタで作ったノードで id を空にしたもの・重複したものは、保存時に `<type の先頭小文字><連番>`（例: `text1`）を付け直す。
- キー順・書式は `serializeProject` が決めるので、手書きの YAML のコメントやキー順は保存すると消える（P0 の仕様どおり）。

## コンポーネント／ダイアログの作成

- 左の「新規作成」で画面・コンポーネント・ダイアログを作る（空の Box をルートにして開く）。
- 右の「ドキュメント」で名前・パスと、params（画面・ダイアログ）/ props（コンポーネント）の定義（名前・TS の型・既定値）を編集する。コンポーネントの props はインスタンスのプロパティ欄に出る。
- 選択したパーツを「コンポーネント化」すると、そのパーツ（と子孫）をコンポーネントの root にして、元の場所をインスタンスに置き換える。
- インスタンスはパレットの「コンポーネント」から置く。「〜を開く」でコンポーネントを編集でき、編集結果はインスタンスのプレビューにすぐ反映される。
- 「events」でクリックなどに画面遷移・ダイアログを開く/閉じるを付けられる（params や setState / updateData は「詳細（JSON）」で編集）。

## 評価（#24）

### 題材画面（S1〜S3）の作成

題材ファイルの S1〜S3 と同じ画面を、エディタの UI 操作だけで新しい画面として組み立て直した（`scripts/rebuild-screens.mjs`。パレットのクリック・レイヤーでの選択・プロパティ欄・style 欄・詳細（JSON）欄への入力を Playwright で操作し、1 回の入力を 1 操作と数える）。保存したファイルの画面を題材ファイルと比べた結果:

| 画面              | ノード数 | 操作数 | うち JSON 欄への入力 | root の一致 | params の一致 | 画面の `events.mount` |
| ----------------- | -------: | -----: | -------------------: | ----------- | ------------- | --------------------- |
| S1 ダッシュボード |       17 |     99 |                    5 | 一致        | 一致          | （なし）              |
| S2 機器一覧       |        5 |     28 |                    2 | 一致        | 一致          | （なし）              |
| S3 機器設定       |       22 |    130 |                   11 | 一致        | 一致          | **作れない**          |

- 3 画面ともノードのツリー（props・style・repeat・visible・events を含む）は題材ファイルと完全に一致し、保存したファイルは `validateProject` を通った。
- JSON 欄で入れたのは events 14 件・repeat 2 件・visible 2 件。events のうち params の無い画面遷移 3 件は events の GUI でも入れられるが、params 付きの遷移・`setState`・`updateData` と repeat / visible は JSON で書くしかない。
- **S3 の画面イベント（`events.mount`）はエディタに編集 UI が無く作れない**（読み込んだファイルの値は保たれる）。
- かかった時間: 自動操作では 3 画面で約 6 秒。人が操作した時間は計測していない。1 操作 5〜10 秒とすると S1 で 8〜16 分、S3 で 11〜22 分ほどの見込み（要実測）。操作の大半は style と props の 1 欄ずつの入力で、`{{ }}` の式は手で打つ必要がある。
- AI での実装時間（git reflog の時刻）: P3-1 着手 08:14 → P3-4 のコミット 08:33。

キャンバスの表示で気づいた点:

- バインディングはサンプルデータで評価して表示する（repeat は 1 件目）。題材の S1 はほぼ実データどおりに見える。
- 画面の params（S3 の `deviceId`）やダイアログの params、`state` の途中の値（S3 の `draftSettings` は mount で入る）はエディタ上に値が無いので、`{{ }}` のまま・空の表示になる。プレビュー用の値を持つ仕組みが要る（P0 に入れるか、エディタ側の設定にするかは要検討）。

### P2（Puck）との比較

P2 は P2-3（#16）まで（コンポーネント／ダイアログの作成は未実装）の時点の main と比べた。

| 観点                             | P2: Puck（完成品エディタ）                                                                 | P3: Craft.js（組み立て型）                                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| エディタの UI                    | Puck 付属（パレット・アウトライン・右パネル・パンくず・undo）                              | すべて自前（パレット・レイヤー・プロパティ・style・リサイズ・ドキュメント切り替え・undo ボタン）                                                   |
| 実装量（src、テスト除く）        | 約 1,030 行（P2-3 時点）＋ CSS 240 行                                                      | P3-3 時点 約 1,780 行、P3-4 まで 約 2,300 行 ＋ CSS 620 行                                                                                         |
| 依存（直接）                     | `@puckeditor/core` のみ。その先に 36 個（dnd-kit・tiptap・radix・zustand・happy-dom など） | `@craftjs/core` のみ。その先は `@craftjs/utils`・immer・lodash・nanoid など 7 個（ほかに評価スクリプト用の devDependency として playwright-core）  |
| ビルドサイズ（JS、gzip 前 / 後） | 約 1.43 MB / 423 kB（CSS 92 kB）                                                           | 約 601 kB / 172 kB（CSS 7 kB）                                                                                                                     |
| ライブラリの状態                 | 活発（0.24 の canary が 2026-09 に出ている）                                               | 0.2.12（2025-02）以降リリースが無い。0.x のまま                                                                                                    |
| パーツの定義                     | Puck の config（fields ＋ render）。欄の種類は Puck の fields に従う                       | resolver に React コンポーネントを登録するだけ。欄は自前なので自由                                                                                 |
| style パネル                     | Puck の `object` フィールド＋カスタム欄。レイアウトの自由度は低い                          | 自由に組める（グループ・2 列・「横並び/縦並び」ボタン・キャンバス上のリサイズハンドル）                                                            |
| P0 との変換                      | Puck の item と P0 の node を 1 対 1。`repeat` などは `props._p0` に退避                   | Craft のノードと P0 の node を 1 対 1。P0 のフィールドを Craft の props にそのまま入れるので退避が要らない                                         |
| ルートが 1 つの P0 との相性      | Puck の `content` は配列なので、`content = [root]` にして 2 つ以上置かれたら警告           | Craft は `ROOT` の 1 ノードから始まるのでそのまま合う                                                                                              |
| コンポーネントのインスタンス     | P2-4 で対応予定                                                                            | resolver が起動時に固定されるので、1 種類の `ComponentInstance` に component id を持たせて描く。エディタで作ったコンポーネントがすぐパレットに出る |
| 複数ドキュメント                 | 画面・ダイアログをタブで切り替え                                                           | 画面・コンポーネント・ダイアログをタブで切り替え（`deserialize`）。undo 履歴は切り替えで消える                                                     |
| ドラッグ＆ドロップ               | dnd-kit（ポインタイベント）                                                                | HTML5 DnD（タッチ非対応、ドロップ位置の表示はシンプル）                                                                                            |

### 持っていける点・持っていけない点

持っていける:

- P0 を唯一の正として持ち、開いているドキュメントの root だけを Craft に読み込んで、変更のたびに P0 に戻す構成。Craft の形式はファイルに出ないので、ライブラリを差し替えても保存形式は変わらない。
- `view.tsx`（パーツの見た目）をキャンバスとコンポーネントのプレビューで共通にしたこと。生成コード（P1）やランタイム（P4）の描画と揃えられる。
- style の欄と候補を `StyleSchema`（zod）から作る方式。
- 実際の Craft の Editor を通した往復テスト（`roundtrip.test.tsx`）と、UI 操作で題材を作り直すスクリプト（`rebuild-screens.mjs`）。

持っていけない・要検討:

- Craft.js 自体。2025-02 以降リリースが無く 0.x のため、本格開発の土台にするなら fork して持つ覚悟が要る。依存が少なく中身も小さい（core 約 370 KB）ので fork は現実的だが、それなら「自作」に近い。
- UI をすべて自作する手間。P2 の約 2 倍のコード量になった。一方で、欲しい UI（style パネル、リサイズ、ドキュメント・コンポーネントの管理）を制約なく作れたのは組み立て型の利点。
- 変更のたびにツリー全体を P0 に変換してプロジェクトを更新しているので、大きな画面では遅くなるおそれがある（題材の規模では問題なし）。
- 画面のイベント・プレビュー用の params / state・コンポーネント id の変更（参照の付け替え）は未対応。

**判断の材料として**: 「完成品に乗る（Puck）」は少ないコードで標準的なエディタが手に入るが、パネルの見た目や操作は Puck の枠に縛られる。「組み立てる（Craft.js）」は自由だが UI をすべて書くことになり、Craft.js が担うのは選択・ドラッグ＆ドロップ・ノードツリー・undo の部分だけ。その部分は比較的小さいため、Craft.js の保守状況も考えると、組み立て型を選ぶなら「Craft.js を土台にする」より「同じ構成で DnD とツリー管理を自作する（または dnd-kit などを使う）」も有力な選択肢になる。
