# @ui-editor/runtime-preview

P4（#25）: データ・バインディング・アクションを実行時に解釈して動かすプレビュー（社内ツールビルダー型）。
題材ファイル `packages/schema/examples/device-monitor.project.yaml` を読み込んで動く。

```sh
pnpm --filter @ui-editor/runtime-preview dev   # http://localhost:5176
pnpm --filter @ui-editor/runtime-preview test
```

評価エンジン（TS 型の解析など、UI に依存しない部分）は [`packages/runtime`](../../packages/runtime) にある。

## 画面

ヘッダーの「開く」で P0 形式のファイル（`.yaml` / `.json`）を読み込み、「保存」で検証してから P0 形式で書き出す（ダウンロード）。開いているタブは URL の hash（`#sampleData` など）に持つ。

| タブ           | 内容                                                                                                                                                                                                                                                                                                |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| プレビュー     | 題材アプリを実行時に解釈して動かす（ノードツリー → React）。バインディングは描画のたびに評価し、イベントは `runActions` で実行する。右側に表示中の画面・ダイアログ、`state`、イベントごとの実行ログ。バインディングのエラーは ⚠（ホバーで内容）で出し、描画は止めない                               |
| データモデル   | `dataModel.source` の型の一覧（オブジェクト型 = データモデル、それ以外 = 型）と詳細。フォームでフィールドを追加・編集すると TS ソースを書き出す（簡易スキーマ定義 UI）。TS ソースの直接編集も可                                                                                                     |
| サンプルデータ | コレクションごとの表。型に合わせた入力（文字列・数値・チェック・列挙の選択、それ以外は JSON）でレコードを編集・追加・複製・削除。型に合わない値はセルを赤くし、一覧に理由を出す                                                                                                                     |
| 式             | バインディング式を試す（入力補完・候補表示つき）。プロジェクト内の式の一覧（場所・その場所で使える名前の静的検査）から選ぶと、スコープにサンプルの `params` / ループ変数などを入れて評価する                                                                                                        |
| イベント       | 画面・ダイアログ・コンポーネントのノードを選び、イベント（`click` / `change` / `rowClick` / 画面の `mount`）にアクションを割り当てる。種類ごとのフォーム（遷移先・ダイアログの選択、params / match / set のキーと値）、並べ替え・削除。「試しに実行」でその場所を表示した状態から実行し、ログを出す |

## 評価メモ

作業時間: #26〜#30 を通して AI 実装で約 1 時間（1 issue = 1 PR を順にマージ）。

### 題材アプリの担当範囲を作れたか

作れた。P0 の題材ファイルをそのまま読み込み、プレビューで次の流れが動く（ヘッドレス Chrome で実際にクリック・入力して確認。同じ流れをアクションの単位で `packages/runtime` の `runtime.test.ts` でも確認。`Preview.test.tsx` は S1 の静的描画のみ）。

| 流れ                        | 結果                                                                                                                     |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| S1 表示                     | 機器カード 5 枚（`StatusBadge` の色分け）、メトリクス 3 枚（64 ℃ / 69.2 % / 1643 Mbps）、最新アラーム 5 件。式のエラー 0 |
| S1 → S2 → S3                | 表の行クリック → `/devices/dev-003`。`mount` で下書きを `state` に用意し、入力の `change` → `setState` で更新            |
| S3 保存 → D1 → 設定更新     | OK で `updateData` ×2 → `closeDialog` → `navigate`。S2 の表の IP が変わり、S3 に戻ると保存した値が出る                   |
| S1 アラーム → D2 → 確認済み | 「確認済みにする」で `updateData` → `closeDialog`。行に「確認済み」が出て、開き直すとボタンが隠れる（`visible`）         |

スキーマ（`packages/schema`）は変更していない。

### `{{ }}` テンプレート形式のバインディングは書きやすく、評価しやすいか

**書きやすさ: 良い。ただし長い式が繰り返される。**

- JS の式がそのまま書けるので、エンジニアには学習コストがほぼ無い。題材の 66 個の式（アロー関数・スプレッド・`?.`・`??`・`toSorted`・オブジェクトリテラルの添字）はすべてそのまま動いた。
- 「文字列全体が 1 つの `{{ }}` なら値そのもの、それ以外は埋め込み」の規則は直感どおりで迷わなかった。
- 一方で、D2 では `data.alarms.find(a => a.id === params.alarmId)` を 5 回書くなど、同じ式が何度も出てくる。画面・ダイアログ単位の名前付きの派生値（`vars`）が欲しい（P0 のメモ 1 と同じ結論）。
- 入力補完（「式」タブ）はサンプルデータの値を辿る方式で作った。`data.devices.find(d => d.` まで補完でき、実用的だった。ただし空の配列や `null`（S3 の `state.draftSettings` の初期値）の先は候補が出ない。`dataModel` の型を使う補完にすれば解決する。

**評価しやすさ: 良い。安全性には割り切りが要る。**

- 評価の本体は、TS のパーサーで検査してから `new Function` で評価する方式で、約 200 行で済んだ（`packages/runtime/src/binding/expression.ts`）。TS はデータモデルの解析のために既にバンドルしているので、検査の追加コストは無い。
- 検査で、使える名前（スコープ＋許可したグローバル）・代入禁止・`constructor` 禁止をかけた。`collectBindings` で「その場所で使える名前」を出せるので、全式の静的検査ができる（題材は全式が合格）。
- 完全なサンドボックスではない（計算したプロパティ名で `constructor` に触れる）。自分で書いた式を動かすエディタなら許容範囲だが、他人の式を動かすなら iframe / SES で隔離する必要がある。方式の比較は [`packages/runtime/README.md`](../../packages/runtime/README.md#安全に評価する方法の選択) に書いた。
- フィールド名の typo（`device.nmae`）は実行しても `undefined` になるだけで見つからない。`dataModel` の型から `.d.ts` を作り、式を TS の型チェッカーにかければ検出できる（lib.d.ts をブラウザに載せる必要がある。未実装）。
- 注意が要ったのは、評価のタイミングが props ごとに違うもの。`Table` の `columns[].value` は行ごとに評価する（`row` が使える）ので、描画側（`Render.tsx`）と静的検査側（`collectBindings`）の両方で特別扱いが要った。「要素ごとに評価するテンプレート」をスキーマで区別できると、部品を足すたびの特別扱いが不要になる。

### 決まった種類のアクションで題材アプリの操作をカバーできるか。足りないアクションは何か

**5 種類で題材はすべてカバーできた。** 連続実行（保存 → 閉じる → 遷移）も、「各アクションは最新のデータで評価し、`params` / `event` は発火した場所のものを使い続ける」という規則で自然に書けた。ランタイムは純粋関数（`runActions(state, actions) → state`）にしたので、React の reducer にそのまま載り、テストも書きやすい。

題材を作る中で足りない・不便だと分かったもの:

| 足りないもの                                        | 理由                                                                                                                                                                |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| レコードの追加・削除（`insertData` / `deleteData`） | `updateData` は既存レコードの更新だけ。機器の追加・アラームの削除のような CRUD が書けない                                                                           |
| レコード全体の置き換え                              | D1 は `network` / `thresholds` / `pollingIntervalSec` を 1 つずつ `set` に書いた。`set: "{{ state.draftSettings }}"` のように丸ごと渡せない（`set` はキーごとの形） |
| 条件分岐（`if`）・失敗時の処理                      | 「入力が不正なら保存しない」「失敗したらメッセージ」が書けない（プロトタイプでは入力チェックは対象外）                                                              |
| 通知（トースト）                                    | 保存後に「保存しました」を出す手段が無い                                                                                                                            |
| 戻る（`navigateBack`）                              | S3 のキャンセルは遷移元に関係なく S2 へ固定で戻る                                                                                                                   |
| 非同期（API 呼び出し）                              | 将来 API から取得する想定だが、`await` やローディング状態の表現が無い                                                                                               |
| コンポーネントの独自イベント                        | `AlarmRow` のクリックは、インスタンスのルート要素のイベントで代用した（P0 のメモ 5 と同じ）                                                                         |

決めたこと: `navigate` は開いているダイアログをすべて閉じる（D1 の OK は明示的に `closeDialog` しているので影響なし）。失敗したアクション（一致するレコードが 0 件の `updateData` など）でそこから先は止める。

### TS 型をスキーマ定義として扱えるか

**扱える。ただし「データの形」までで、制約や UI 向けの情報は別に要る。**

- TypeScript Compiler API（構文木だけ、型チェッカーなし）で、`interface` / `type` をフィールド一覧（名前・型・必須・JSDoc）に変換するのは約 220 行で済んだ。題材の型はすべて解釈でき、TS に書き戻しても一致する（往復のテストあり）。
- 同じ解析結果で、サンプルデータの型検査（不一致・必須の欠落・余分なフィールド）、レコード追加時の初期値、表の入力部品の選択（列挙 → セレクト、boolean → チェックボックス）まで作れた。
- 対応はサブセット（プリミティブ・リテラル・配列・オブジェクト・ユニオン・型名の参照）。ジェネリクス・`extends`・交差型・`Record` などは診断を出して扱わない。データモデルにはこれで足りた。
- 不便な点:
  - **コレクションと型の対応がスキーマに無い**。`sampleData.devices` が `Device[]` であることを名前の規約（`devices` → `Device`）で推測した。#2 に報告済み。
  - **制約が書けない**。IP アドレスの形式・数値の範囲（閾値 0〜120）・表示名は TS 型に無い。JSDoc のタグ（`@min` など）で補うか、zod / JSON Schema に寄せる判断が要る。
  - **フォームで編集するとソースを書き直す**。`printDataModel` で再生成するので、TS ソースに書いたコメントの位置や書式は保たれない（JSDoc は保つ）。
  - **バンドルが大きい**。ブラウザで `typescript` を使うため、JS が約 3.9 MB（gzip 1.1 MB）になる。解析だけなら軽いパーサーに替えるか、Web Worker で遅延読み込みする。TS 7 系での動作は未検証のため、6 系に固定した。

### 生成コード（P1 の基準）

P4 はコードを生成しない（定義を実行時に解釈する方式）ため対象外。ただし `runActions` の振る舞い（連続実行の規則など）は、生成コードのストアが満たすべき仕様の参考になる。

### パーツを 1 種類追加する手間

- **コンポーネント（ユーザー定義）**: コードの変更は不要。プロジェクトファイルの `components` に書けば、プレビュー・式の検査・イベント設定にそのまま出る。
- **組み込みのノード**（例: `Select`）: 次の 3〜4 か所。
  1. `packages/schema` の `BUILTIN_NODE_TYPES` に追加（検証で未知の type にならないように）
  2. `src/preview/Render.tsx` の `switch` に描画を追加（20〜30 行＋ CSS）
  3. `src/actions/edit.ts` の `eventNamesFor` にイベント名を追加
  4. 要素ごとに評価する props があれば、`collectBindings` と描画の両方で特別扱い（`Table` の `columns` と同じ）

### プロジェクトファイル（P0 形式）で表現しきれたか。スキーマに不足はあったか

題材は P0 形式のまま動いた。実行時に解釈してみて分かった不足:

1. コレクションとデータモデルの型の対応（#2 に報告済み）
2. 要素ごとに評価するテンプレート（`Table` の `columns[].value`）を区別する手段
3. 名前付きの派生値（`vars`）
4. レコードの追加・削除のアクション、`updateData` の全体置き換え
5. コンポーネントの独自イベント
6. `ParamDef.type` / `StateDef.type` の型式と `dataModel` の対応は文字列だけ。今回は `parseTypeExpression` で解釈して、サンプルの params を作るのに使った

### 本格開発にそのまま持っていけそうな点、持っていけない点

**持っていけそう**

- `packages/runtime` は UI に依存しない純粋な関数だけでできている。エディタのプレビューにも、P1 の生成コードのストアの振る舞いの基準（テストの期待値）にも使える。
- アクションを「状態 → 状態」の純粋関数にした設計。reducer に載り、ログ・やり直し・テストが簡単。
- `collectBindings` による「その場所で使える名前」の一覧。式の静的検査・補完・P5 の遷移図（`navigate` の抽出）に使える。
- TS 型 → フィールド一覧の変換と、サンプルデータの型検査。

**持っていけない・作り直しが要る**

- `new Function` の評価は、他人が書いた式を動かすなら隔離（iframe / SES）が要る。
- `typescript` 丸ごとのバンドル（3.9 MB）。
- 値ベースの入力補完。型ベースにしないと、空データの先が補完できない。
- UI は各タブとも最小限（アクション設定は種類ごとのフォームを手で並べただけ）。本格的な画面エディタ（P2 / P3）と統合する前提で作り直す。
