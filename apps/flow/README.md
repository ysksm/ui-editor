# @ui-editor/flow（P5 画面遷移図）

Figma のプロトタイプモードのように、画面・ダイアログをノード、イベント → `navigate` / `openDialog` をエッジとして表示するプロトタイプ（#31）。

## 起動

```sh
pnpm install
pnpm --filter @ui-editor/schema build   # 初回のみ（flow は schema の dist を読む）
pnpm --filter @ui-editor/flow dev       # http://localhost:5177/
```

## できること（P5-1）

- 題材ファイル [`device-monitor.project.json`](../../packages/schema/examples/device-monitor.project.json) を読み込んで遷移図を描く。ツールバーの「ファイルを開く」で他の P0 形式のファイル（JSON / YAML）も読める
- ノード: 画面・ダイアログのノードツリーを簡易なワイヤーフレームで描く（バインディングは評価せず、式を短く表示）。`repeat` は `×n`、式の `visible` は `if` のバッジ
- エッジ: 遷移の起点パーツ（ボタン・カード・テーブル行など）から出る。`navigate` は実線、`openDialog` は破線。ラベルはイベント名
- 自動レイアウト（dagre、左 → 右）と手動配置。ドラッグ後に「配置を保存」で `layouts/<名前>.layout.json` に書き込む

## 遷移の編集（P5-2）

- **追加**: ノードにマウスを乗せると、遷移を引き出せるパーツ（ボタン・テーブル・コンポーネントのインスタンス・`cursor: pointer` の Box・イベントを持つノード）の右端に点が出る。そこから画面・ダイアログへドラッグすると、パーツのイベントの末尾にアクションを足す
  - 遷移先が画面なら `navigate`、ダイアログなら `openDialog`
  - イベントは type で決める（`Table` → `rowClick`、入力系 → `change`、ほか → `click`）。パネルで付け替えられる
  - 遷移先の必須の params は、遷移元に同じ名前の params があれば `{{ params.x }}`、無ければ空文字で入れる（パネルで入力する。空のままでも検証は通るので、赤枠で示す）
- **削除**: 線を選んで Delete / Backspace、またはパネルの「この遷移を削除」。アクションを消し、空になったイベント・`events` も消す。同じイベントの他のアクション（`closeDialog` など）は残す
  - コンポーネント内に書かれた遷移は、コンポーネントの定義から消える（そのコンポーネントを使うすべての場所に効く）
- **パネル**: 選んだ線の起点・イベント・アクション・params を表示し、イベントと params を編集できる
- **保存**: 「プロジェクトを保存」で P0 形式（`serializeProject`）で書き出す。File System Access API のあるブラウザ（Chrome / Edge）では開いたファイルに上書きし、題材ファイルのように開いていない場合は保存先を選ぶ。API が無ければダウンロード
- ツールバーに検証（`validateProject`）の結果を常に表示する

## 構成

| ファイル                   | 内容                                                                             |
| -------------------------- | -------------------------------------------------------------------------------- |
| `src/graph/extract.ts`     | P0 のプロジェクト → ノード（画面・ダイアログ）と遷移。遷移ごとに起点の住所を持つ |
| `src/graph/edit.ts`        | 遷移の追加・削除・付け替え・params 編集を P0 データに反映（コピーを返す）        |
| `src/graph/layout.ts`      | dagre による自動配置と、保存済み位置とのマージ                                   |
| `src/graph/layout-file.ts` | 配置ファイルの読み書き                                                           |
| `src/nodes/`               | 画面ノードとワイヤーフレーム                                                     |
| `vite.config.ts`           | 配置ファイルを書き込む開発サーバー用 API（`POST /api/layout?name=`）             |
| `layouts/`                 | 保存した手動配置位置                                                             |

### 遷移の取り出し方

- アクションの置き場所: 画面の `events`（`mount`）、画面・ダイアログ内の各ノードの `events`、コンポーネント内のノードの `events`（インスタンスを置いた画面・ダイアログから出る遷移として扱う）
- 遷移の id は起点の住所（`screen:dashboard/alarmRow#click[0]` = 画面 `dashboard` のノード `alarmRow` の `click` の 0 番目のアクション）。P5-2 で遷移を追加・削除するときにこの住所で P0 データを書き換える
- `closeDialog` は遷移先が決まらない（開いた元に戻る）ので、エッジにしない

### 手動配置位置の置き場所

スキーマ v0 には配置位置を保存する場所が無い（プロジェクトは未知のキーを許さない）。`packages/schema` は変更しない方針なので、`apps/flow/layouts/` に別ファイルとして保存する。書き込みは開発サーバーの API で行うため、`vite preview` などでは代わりにファイルとしてダウンロードする。

## プロトタイプモード（P5-3）

- ツールバーの「▶ プロトタイプ」（選んでいる画面、無ければ開始画面から）か、ノードのダブルクリック（その画面・ダイアログから）で始まる
- 画面をワイヤーフレームで大きく描き、ホットスポット（遷移に関わるアクションを持つパーツ）をクリックするとアクションを順に実行する
  - `navigate` → 画面を切り替える。移った先の `mount` も実行する（`mount` の `navigate` はリダイレクトとしてたどる。ループは 10 回で止める）
  - `openDialog` → ダイアログを画面の上に開く（下の画面は操作できない）。`closeDialog` → 閉じる
  - ダイアログは同時に 1 つだけ（`openDialog` は開いているものを置き換える）で、`navigate` では閉じない。P1-4 の生成コード（ストアの `dialog: { id, params } | null`）に合わせた
  - `setState` / `updateData` は実行せず、ログに「実行しない」と残す。バインディングも評価しない（params は式のままログに出す）
- ホットスポット以外をクリックすると、クリックできる場所が一瞬光る（Figma と同じ）。「クリックできる場所を表示」で常に表示
- 「戻る」（直前の状態）、「最初から」、右側に実行したアクションのログ。「遷移図に戻る」と、最後に見ていた画面・ダイアログを遷移図で選んで寄せる

## 評価メモ

### 題材の担当範囲を作れたか

作れた。P5-1〜P5-3 を AI 実装の 1 セッション（1 時間未満）で作った。

- 題材の 5 画面（S1〜S3, D1, D2）がノードになり、8 本の遷移がエッジとして起点のパーツから出る
- 遷移の追加・削除・イベントの付け替え・params の編集が P0 データに反映され、P0 形式で保存できる（変換テスト 13 件。追加・削除した結果を JSON / YAML で書き出して読み戻すと一致し、検証を通る。消して同じ遷移を足し直すと題材ファイルと同じテキストになる）
- プロトタイプモードで S1 → D2 → S1 → S2 → S3 → D1 → S2 を再生できる

### 操作感

- **良かった点**
  - 線がボタン・機器カード・テーブル・アラーム行など**起点のパーツから出る**ので、「どのボタンでどこへ行くか」が一目で分かる。React Flow のカスタムノードの中にハンドルを置くだけで実現できた
  - パーツの点から画面へドラッグ → P0 のイベントにアクションが入る → 線が引かれる、が即座につながる。ツールバーの検証表示で、params の入れ忘れなども分かる
  - プロトタイプモードは「クリックできる場所が光る」「戻る」「ログ」があるだけで、画面のつながりを確かめる用途には十分だった
- **良くなかった点**
  - 8 本でもう線が画面ノードの上を横切る。画面ノードが大きい（フォームのある S3 は縦に長い）ため、ベジェ曲線がノードをまたぎやすい。dagre の自動配置は 5 ノードなら十分だが、画面が増えるとエッジの経路（ルーティング）を工夫しないと読めなくなりそう
  - ワイヤーフレームはバインディングを評価しないので `{…}` だらけになり、画面の見分けがつきにくい。サンプルデータで評価した実際の描画（縮小サムネイル）の方がよい
  - 起点パーツの点はノードにマウスを乗せたときだけ出す（常に出すとうるさい）。そのため最初は「どこから線を引けるか」に気付きにくい
  - `repeat` の中のパーツ（機器カード・アラーム行）は 1 つの点にまとまる。「どの行か」は params（`{{ alarm.id }}`）で決まり、図では表せない
  - プロトタイプモードもバインディングを評価しないため、S3 では「機器が見つかりません」とフォームが両方出る（`visible` を評価しない）。見た目の確認には P4 のランタイムが要る

### 画面エディタ（P2 / P3）との役割分担

| 対象                                      | 遷移図（P5）                           | 画面エディタ（P2 / P3）           |
| ----------------------------------------- | -------------------------------------- | --------------------------------- |
| 画面・ダイアログのツリー、props、style    | 読むだけ（ワイヤーフレーム）           | 編集する                          |
| `navigate` / `openDialog`（遷移）         | 追加・削除・イベントの付け替え・params | —                                 |
| `closeDialog` / `setState` / `updateData` | 読むだけ（再生時にログ）               | イベントパネルで編集（P4 の範囲） |
| 画面・ダイアログの追加・削除・id の変更   | しない                                 | する                              |

- P2 は `events` を `_p0` に退避して編集しない、P3 は props としてそのまま通す。どちらも遷移を編集しないので、遷移図と役割はぶつからない
- ただし `events` という同じデータの中に「遷移図が触るアクション」と「画面エディタ（P4）が触るアクション」が混ざる。今回は遷移図側が**他のアクションを残したまま**、遷移のアクションだけを足し引きするようにした（D1 の OK ボタンのように `updateData` ×2 → `closeDialog` → `navigate` と並ぶ場合も壊さない）

### 統合する場合の課題

- **1 つのプロジェクトを複数のビューで編集する仕組み**: 遷移図と画面エディタが同じプロジェクト（メモリ上）を共有し、`edit.ts` のような「住所を指定した操作」で書き換える形にする。Undo / Redo もそこに集める。今回の遷移図は自分の中に状態を持っているだけ
- **アクションの住所**: 今は「画面 / ノード id / イベント / アクションの番号」で指している。番号は他の編集（同じイベントへのアクションの追加・並べ替え）でずれる。アクションに id を持たせるか、編集のたびに住所を引き直す必要がある
- **ノード id の変更・画面の削除**: 画面エディタで id を変えたり消したりしたとき、`navigate.to` などの参照と配置位置を一緒に直す必要がある（下の「配置位置」も参照）
- **選択の同期**: 遷移図でパーツを選ぶ → 画面エディタでそのノードを選ぶ、の往復があると便利。ノード id が画面の中で一意なので実装はしやすい
- **描画の共通化**: ワイヤーフレームは遷移図専用の簡易描画。統合するなら画面エディタのキャンバス（または P4 のランタイム）を縮小して使い、プロトタイプモードも P4 のランタイム（バインディング・`setState` を評価する）にホットスポットの表示を足す形にしたい

### P0 形式で表現しきれたか・スキーマに不足はあったか

遷移の表示・編集・再生は P0 v0 で表現できた（`navigate.to` / `openDialog.dialog` が固定 id なので、ファイルから静的に遷移図を作れる）。気になった点:

1. **エディタ用の情報（配置位置）の置き場所が無い**（下で詳しく）
2. **コンポーネントのイベントの定義が無い**: `AlarmRow` のインスタンスに `click` を書いているが、コンポーネントがどのイベントを出すかはスキーマに無い。遷移図で線を引くとき、インスタンスには `click` を決め打ちしている
3. **params の既定値を決められない**: 遷移を足すとき、遷移先の必須 params（`deviceId` など）の式は起点の文脈（`repeat` の変数 `device`、テーブルの `event.row`）で変わる。遷移図からは分からないので、遷移元に同じ名前の params があるときだけ `{{ params.x }}` を入れ、ほかは空文字にしてパネルで入力してもらう。空文字でも検証は通ってしまう
4. **`closeDialog` の戻り先・「戻る」**: `closeDialog` は開いた元に戻るので遷移図では線にしない。ブラウザの「戻る」に当たるアクションも無い
5. **ダイアログの開き方の意味がスキーマに書かれていない**: 同時に開けるのは 1 つか、`navigate` で閉じるか。P1-4 が「同時に 1 つ・`navigate` では閉じない」と決めたので、プロトタイプモードもそれに合わせた（最初は「重ねて開ける・`navigate` で閉じる」で作っていた）。スキーマの README に明記し、P4 のランタイムとも揃えたい

### 配置位置をプロジェクトファイルに入れるか（#34 のコメントへの回答）

**別ファイルにして困った点**（`layouts/<名前>.layout.json`、画面・ダイアログ id → 座標）

- **id を変えると位置を失う**: 新しい id は保存済みの位置に無いので自動配置の位置に置かれる。自動配置は保存済みの位置を考えずに計算するため、ほかの画面と重なることがある。古い id の座標はファイルに残る（次に「配置を保存」するまで）
- **画面を消すと座標が残る**: 同上。表示には影響しないが、ファイルにゴミが残る
- **プロジェクトファイルとの対応がファイル名だけ**: ファイル名を変える・別の場所で開くと配置を失う。ブラウザから任意の場所のファイルを開いた場合も、配置は `apps/flow/layouts/` という別の場所に保存される（開発サーバーの API が無いとダウンロードになる）
- **git の差分が 2 つのファイルに分かれる**: 画面を足したコミットと配置を直したコミットがずれやすい

**提案: 入れる。トップレベルに `editor` の名前空間を足す**

```yaml
editor: # エディタだけが使う情報。コード生成・ランタイムは読まない
  flow:
    positions:
      dashboard: { x: 20, y: 201 }
      devices: { x: 462, y: 20 }
```

- 画面の定義（`screens[]`）の中ではなく、トップレベルの 1 か所にまとめる。画面を動かしただけの差分が画面の定義に混ざらず、`KEY_ORDER` で末尾に置けば差分も読みやすい
- id の変更・削除はどのみち `navigate.to` などの参照を直す操作が要るので、そのときに `editor.flow.positions` も直す。`validateProject` で「存在しない id の座標」を警告にすれば、ゴミも見つけられる
- `editor` の中身はエディタごとに自由（`flow` のほか、画面エディタのズームや折りたたみなど）にし、スキーマでは `flow.positions` だけ形を決める
- 画面ごとに `screens[].editor.position` を持たせる案は、id の変更・削除に自動で追従する利点があるが、アプリの定義とエディタの情報が混ざるので採らない

### パーツを 1 種類追加する手間

遷移図側はほぼゼロ。コンポーネントは何もしなくてよい（名前付きの点線の枠と中身のワイヤーフレームで描かれ、`click` で線を引ける）。組み込みのパーツを足す場合は、ワイヤーフレームの描き方（`Wireframe.tsx` の `case`、10 行程度。無くてもコンポーネントと同じ枠で描かれる）と、線を引くときのイベント（`eventsForType` に 1 行）を足す。

### 実装量と依存ライブラリ

- 実装: TS / TSX 約 1,700 行（うち純粋関数の `graph/` と `prototype/player.ts` が約 620 行、UI が約 1,100 行）、CSS 約 640 行、テスト約 480 行（27 件）
- 依存: `@xyflow/react`（React Flow 12、MIT）、`@dagrejs/dagre`（自動配置）、`react` / `react-dom` 19。ビルド結果は JS 約 730 KB（gzip 約 215 KB。zod・yaml・React Flow を含む）

### 本格開発にそのまま持っていけそうな点・持っていけない点

- **持っていける**
  - React Flow を土台にすること。カスタムノードの中に起点パーツごとのハンドルを置く方式、ハンドル以外（ノード本体）に落としても繋がる操作
  - `extract.ts`（プロジェクト → 遷移）、`edit.ts`（住所を指定した編集。他のアクションを壊さない）、`player.ts`（再生の意味）と、それぞれのテスト
  - 遷移図が編集するのは `navigate` / `openDialog` だけ、という役割の分け方
- **持っていけない**
  - ワイヤーフレーム（画面エディタのキャンバスか P4 のランタイムの縮小表示に置き換える）
  - 配置位置の別ファイルと開発サーバーの API（`editor` の名前空間に移す）
  - 保存（File System Access API はブラウザ依存。Tauri ならネイティブのファイル操作になる）
  - `App.tsx` に状態を持つ作り（統合するなら共有のストア＋Undo / Redo にする）
  - エッジの描き方（画面が増えたときのルーティング）は要検討
